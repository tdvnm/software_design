Components and technology stack

The technologies and components used in this prototype, and how they relate to Homework 2.

Technology stack

TechnologyWhat we use it for
HTMLPage structure, labelled forms and the trimester table.
TypeScriptCourse and plan types, browser events and data operations. Compiled to native JavaScript modules.
Sass / CSSShared colour and spacing variables, cards, controls and responsive layouts.
Node.js HTTPThe built-in node:http module serves pages, assets and the health endpoint.
SQLiteThe built-in node:sqlite module creates tables and imports the course CSV. The browser is not connected to it yet.
Node.js test runnernode:test checks CSV parsing, plan operations and server routes.

TypeScript and Sass are the only npm build dependencies. The prototype has no frontend framework, backend framework or ORM.

Frontend components

ModuleResponsibility
components/programme.tsMajor/minor selectors and the plan label.
components/catalogue.tsCourse search, subject filters, Details and Add buttons.
components/board.tsThe four-year trimester table, placements, removal and credit totals.
components/details.tsThe selected course's title, subjects, credits and description.
main.tsStartup, loading/error messages and callbacks that connect the components.
plan.tsIn-memory plan operations, duplicate prevention and credit sums, independent of the DOM.
data/catalogue.ts and lib/csv.tsDownload the course snapshot and parse CSV fields.

When a student presses Add, the catalogue calls a callback in main.ts. That calls addCourse in plan.ts, then redraws the board and totals. No server request is made for that edit.

HW2: the full system design

Assignment 2 laid out the full system as eight components. This is how much of each the prototype contains.

Component Responsibility Runs In this prototype
Client Subject pickers, a course catalogue, a year × trimester grid, a details panel. Browser Yes, simplified. Ordinary buttons and selects instead of drag-and-drop.
API The contract between browser and server: catalogue read, plan create/read/update/delete. Server GET /api/health only. Plan routes are documented, not built.
Catalogue store Courses, subjects and the links between them. Database Yes: three tables filled by npm run db:import.
Plan store One student, several named plans, each a set of (course, year, trimester) placements. Database Tables exist; nothing writes to them yet.
Ingest pipeline Read the timetables and programme pages, resolve prerequisites, write the catalogue. Batch Not started. The CSV is a one-off export of that work.
Deadline engine The last trimester a programme can still be declared, and the course that breaks first. Server Not started.
Rule engine Credit floors and caps, prerequisite order, offering trimester, eligibility, in plain words. Shared Not started.
Identity Sign-in with the university account, sessions, read-only share links. Server Not started.

HW2 proposed Svelte and PostgreSQL. This prototype uses vanilla TypeScript and SQLite. The ingest pipeline, deadline engine, shared rule engine and identity component are future work.
