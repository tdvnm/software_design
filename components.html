Components and technology stack

The technologies and components used in this prototype, and how they relate to Homework 2.

Technology stack

TechnologyWhat we use it for
HTMLPage structure, labelled forms and the trimester table.
JavaScriptNative browser modules, DOM events and plan operations. No compiler or bundler.
CSSShared colour and spacing variables, cards, controls and responsive layouts.
PythonThe standard-library http.server module serves pages, assets and the course/plan API. No web framework.
SQLite3Python's built-in sqlite3 module creates the tables, imports the course CSV and answers the API's queries. The planner reads courses through GET /api/courses.
Testsnode:test checks CSV parsing and plan operations in the browser code; unittest checks the server's routes and API.

There are no npm dependencies, and the server needs nothing beyond Python's standard library. The prototype has no frontend framework, backend framework or ORM.

Frontend components

ModuleResponsibility
components/programme.jsMajor/minor selectors and the plan label.
components/catalogue.jsCourse search, subject filters, Details and Add buttons.
components/board.jsThe four-year trimester table, placements, removal and credit totals.
components/details.jsThe selected course's title, subjects, credits and description.
main.jsStartup, loading/error messages and callbacks that connect the components.
plan.jsIn-memory plan operations, duplicate prevention and credit sums, independent of the DOM.
data/catalogue.js and lib/csv.jsFetch course JSON from the API; parse the CSV in data tests.

When a student presses Add, the catalogue calls a callback in main.js. That calls addCourse in plan.js, then redraws the board and totals. No server request is made for that edit.

HW2: the full system design

Assignment 2 laid out the full system as eight components. This is how much of each the prototype contains.

Component Responsibility Runs In this prototype
Client Subject pickers, a course catalogue, a year × trimester grid, a details panel. Browser Yes: buttons, selectors, drag-and-drop, course details and trimester zoom.
API The contract between browser and server: catalogue read, plan create/read/update/delete. Server Catalogue, health and plan CRUD routes are implemented. The UI calls the catalogue route.
Catalogue store Courses, subjects and the links between them. Database Yes: three tables filled by npm run db:import.
Plan store One student, several named plans, each a set of (course, year, trimester) placements. Database Plan API writes these tables. The current UI saves its active plan in localStorage.
Ingest pipeline Read the timetables and programme pages, resolve prerequisites, write the catalogue. Batch Not started. The CSV is a one-off export of that work.
Deadline engine The last trimester a programme can still be declared, and the course that breaks first. Server Not started.
Rule engine Credit floors and caps, prerequisite order, offering trimester, eligibility, in plain words. Browser Advisory load, prerequisite, eligibility and historical-offering checks; full degree validation is future work.
Identity Sign-in with the university account, sessions, read-only share links. Server Not started.

HW2 proposed Svelte and PostgreSQL. This prototype uses plain JavaScript and SQLite. Live ingestion, declaration deadlines, complete degree validation and identity are future work.
